# Native unlock events and frame pacing: platform evidence

- `KeyguardManager.isKeyguardLocked()` reports whether keyguard is logically showing; it cannot distinguish failed authentication from no attempt (and showing does not mean credentials are necessarily required). `isDeviceLocked()` is a lock-state query, not a failure event. https://developer.android.com/reference/android/app/KeyguardManager
- `ACTION_USER_PRESENT` means the user is present after wake, e.g. keyguard gone. It is not an attempt or failure event. https://developer.android.com/reference/android/content/Intent#ACTION_USER_PRESENT
- `DeviceAdminReceiver.ACTION_PASSWORD_FAILED` / `onPasswordFailed` is a documented *device or profile challenge password* failure event. It is sent to a device administrator that declared `USES_POLICY_WATCH_LOGIN`; the metadata policy is `watch-login`. This cannot be equated with every failed fingerprint, nor assumed reliable across Samsung versions without testing. https://developer.android.com/reference/android/app/admin/DeviceAdminReceiver#ACTION_PASSWORD_FAILED https://developer.android.com/reference/android/app/admin/DeviceAdminInfo#USES_POLICY_WATCH_LOGIN
- Device-admin activation is a separate user-granted administrative capability; it must not be silently enabled or presented as a harmless animation requirement. Samsung Knox management enrollment likewise requires admin activation and can involve licensing; Samsung's own error documentation identifies activation failure when end-user permission is not given. https://developer.android.com/guide/topics/admin/device-admin https://docs.samsungknox.com/admin/knox-manage/new-console/references/android-agent-error-codes/
- `BiometricPrompt.AuthenticationCallback.onAuthenticationFailed` concerns the `BiometricPrompt` session hosted by the app's own activity/fragment, not a passive subscription to One UI keyguard. Running a separate prompt would change the user's flow and does not evidence a native lock-screen failure. https://developer.android.com/reference/androidx/biometric/BiometricPrompt https://developer.android.com/reference/androidx/biometric/BiometricPrompt.AuthenticationCallback
- Inference from the above: there is no demonstrated public ordinary-app API covering both native One UI PIN and fingerprint failure events. Do not label a keyguard state, timer, or unlock broadcast as a failed attempt. With the stipulated no-root/no-flash/native-auth constraints, implement a clearly labeled manual DEMO pulse in full-screen preview/settings; leave actual failure-triggered behavior unclaimed until real device evidence establishes an explicitly authorized route. Wallpaper visibility behind Samsung's security UI is also device-dependent and unverified.

## Rendering and validation

- `Surface.setFrameRate(120f, ...)` (API 30+) communicates intended frame rate; system *may* select an appropriate refresh rate. It neither guarantees 120 Hz nor throttles frame production. Observe display changes using `DisplayManager.registerDisplayListener`. https://developer.android.com/reference/android/view/Surface#setFrameRate(float,int) https://developer.android.com/media/optimize/performance/frame-rate
- Choreographer coordinates work with display timing. `postFrameCallback` is a one-shot and needs reposting; on API 33+ `postVsyncCallback` offers frame timeline data. The current Android documentation recommends `FrameData.getAnimationTimeNanos()` for animation timing rather than `FrameCallback`'s frame-start timestamp. https://developer.android.com/reference/android/view/Choreographer https://developer.android.com/reference/android/view/Choreographer.FrameCallback
- EGL swap interval alone cannot prove steady frame delivery or 120 Hz; composition, hardware refresh selection, missed deadlines, and buffering matter. Android frame-pacing documentation discusses timing, presentation timestamps, and sync fences. https://source.android.com/docs/core/graphics/frame-pacing
- Desktop browser or video preview confirms appearance only. Actual One UI lock-screen wallpaper visibility, native event semantics, refresh rate, frame cadence and power behavior require an installed device test. With ADB disconnected, no such verification or 120 Hz claim is justified.
